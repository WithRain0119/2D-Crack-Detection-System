# 水工建筑物智能巡检分析系统

## 背景

本项目为华北水利水电大学校级大创项目，核心功能为对水工建筑物表面的裂缝进行识别。未来会逐步地扩展识别缺陷的种类。

## 项目技术栈

| 层级 | 技术选型 | 说明 |
|---|---|---|
| 深度学习框架 | PyTorch（CPU 版）+ Ultralytics | YOLO 目标检测框架，加载本项目训练好的权重 `version2.pt`（crack 单类别） |
| 后端框架 | Python 3.12 + FastAPI + Uvicorn | 轻量异步 Web 框架，提供批次管理、识别推理、历史查询等 REST 接口 |
| 数据存储 | SQLite（Python 标准库 `sqlite3`） | 检测历史持久化，重启后可查，零额外部署成本 |
| 图像处理 | Pillow（PIL） | 图片合法性预检、识别结果图绘制保存 |
| 前端 | 原生 HTML5 + CSS3 + JavaScript | 零框架、零 CDN、无任何外部网络依赖，浏览器直接打开即可使用 |
| 运行环境 | Windows + Conda（`yolo_v1` 环境） | 单机本地部署，前后端通过本地 HTTP 接口通信 |

## 声明

当前系统并非最初的版本，因最初版本bug较多，结构混乱，维护较为困难，因此此版本是根据最初的版本进行**重构的版本**。

## 一、重构步骤

本次重构按"**后端 → 前端 → 文档 → 验收**"四个步骤分步实施，每一步独立测试通过后再进入下一步，保证每一步都可验证、可回退。

### 步骤一：后端重构

**采用技术**：Python 3.12 + FastAPI + Ultralytics YOLO + SQLite + 多线程推理。

**如何重构**：将最初版本混乱的后端代码拆分为 8 个单一职责模块，统一按接口契约实现，核心改动包括：

1. **模块化拆分**——每个文件只负责一件事，模块间单向依赖，消除原版本职责纠缠、难以维护的问题；
2. **批次流水线**——"创建批次 → 图片落盘 → 后台逐张识别 → 结果图输出"四段式流程，图片按上传时间归档到 `static/<批次时间>/input|output/`；
3. **SQLite 持久化**——检测记录（上传了哪些图、存在哪里、识别效果）写入 `backend/history.db`，重启后历史不丢失；
4. **单实例保护与运行日志**——进程锁防止重复启动；每次启动自动生成带时间戳的日志文件，全链路记录启动、请求、推理、异常信息，便于排查问题；
5. **推理与服务解耦**——YOLO 推理固定在独立线程池中串行执行，接口响应不被慢速推理阻塞。

**实现的功能**：后端健康检查、批次创建与上传（含同名去重、非图片过滤、500 张上限）、启动识别、进度轮询、历史批次列表、检测记录查询、单张兼容检测、清空日志。

**文件功能说明**：

| 文件 | 功能 |
|---|---|
| `backend/main.py` | 程序入口：按顺序执行"目录自检 → 抢占实例锁 → 初始化日志 → 加载模型 → 恢复历史批次 → 启动服务" |
| `backend/config.py` | 全局常量集中定义：地址端口、模型路径、时间格式（日志与批次命名统一）、图片扩展名白名单、数量上限等 |
| `backend/logger.py` | 日志系统：每次启动在 `log/` 下新建一个时间戳日志文件，控制台与文件双路同步输出 |
| `backend/lock.py` | 工作目录自检（必须从项目根目录启动）+ 单实例锁（原子创建锁文件、进程存活探测、残留锁自动清理） |
| `backend/yolo.py` | 模型加载与单图推理：图片合法性预检 → CPU 推理 → 输出裂缝框、裂缝数量、图像尺寸、耗时 → 绘制并保存结果图 |
| `backend/history.py` | SQLite 检测历史读写：建表、每张图识别完成即入库（成功与失败都记录）、按批次/全量查询 |
| `backend/batches.py` | 批次核心逻辑：批次创建与图片存储、同名去重、后台识别任务调度、进度状态维护、启动时扫描磁盘恢复批次 |
| `backend/routes.py` | HTTP 接口层：注册全部路由、跨域配置、每个请求的方法/路径/状态码/耗时日志中间件、静态图片服务 |

**如何测试**：

1. 从项目根目录启动后端，观察 `log/` 下生成新日志文件、控制台无异常堆栈；
2. 浏览器访问 `http://127.0.0.1:8000/`，确认返回 `"model_loaded": true, "model_path": "version2.pt"`；
3. 用 `curl` 依次调用批次接口：上传图片 → 启动识别 → 轮询进度至完成，核对 `static/` 下 `input/` 原图与 `output/` 结果图一一对应；
4. 负例测试：不带文件上传、上传非图片文件、伪造损坏图片、查询不存在批次，确认均有明确错误提示且不崩溃；
5. 重启后端，确认历史批次列表与检测记录仍在（SQLite 持久化生效）；
6. 启动第二个实例，确认打印"已有实例正在运行"并退出。

### 步骤二：前端重构

**采用技术**：原生 HTML5 + CSS3 + JavaScript，三个文件组成（主页面 + 样式 + 脚本），无任何框架和外部 CDN 依赖，断网环境可用。

**如何重构**：针对最初版本前端的十余处缺陷逐条规避重写——固定页面结构配合显隐切换（不再用字符串拼接重建界面）、所有用户数据用 `textContent` 输出（杜绝注入）、轮询引入取消机制（切换批次即作废旧轮询）、进度条直接读取后端真实进度（不再前端模拟）等。

**实现的功能**：

1. **三种选图方式**：选择整个文件夹、选择单/多张图片、拖拽上传；
2. **置信度调节**：滑块调整识别阈值（0.05~0.9），随本次分析生效；
3. **实时进度**：进度条、已处理张数、当前识别文件名；
4. **结果查看**：左侧缩略图列表（待处理/处理中/完成/失败四态标注），右侧原图与识别结果大图对比，点击切换；
5. **裂缝明细表**：每条裂缝的像素坐标、归一化坐标、置信度，表格列与表头严格对应；
6. **历史记录栏**：显示上传文件名、存储位置、识别时间、裂缝数量与结果缩略图，后端重启后仍可查看；
7. **设置面板**：右上角齿轮按钮，内置清空历史日志功能，预留后续扩展；
8. **状态提示**：后端未连接（红色）、模型未加载（黄色）、在线（绿色）三态提示，异常不白屏。

**文件功能说明**：

| 文件 | 功能 |
|---|---|
| `水工建筑物智能巡检分析系统.html` | 页面主结构：状态栏、操作区、进度区、结果区、历史记录区、设置面板的固定骨架 |
| `assets/style.css` | 全部样式：深色科技风视觉（毛玻璃卡片、荧光强调色、状态徽章、进度条动效等），响应式布局 |
| `assets/app.js` | 全部交互逻辑，按模块分区：后端探测、文件过滤、上传分析、进度轮询、结果渲染、明细表、历史记录、设置面板 |

**如何测试**：

1. 断网打开页面：样式正常、无任何外部网络请求（浏览器开发者工具 Network 面板核验）；
2. 后端未启动时打开页面：顶部红色提示、分析按钮禁用；启动后刷新转为在线绿色；
3. 选择"3 张图片 + 1 个 txt"的文件夹：提示 3 张有效、txt 跳过，进度从 0/3 到 3/3，磁盘批次目录与页面提示一致；
4. 混入一张损坏图片：该张红色标注"失败"，其余正常完成，页面不崩溃；
5. 点击缩略图切换大图与明细表，数字与表格同步变化；归一化坐标在 0~1 之间；
6. 历史记录区正常列出（非空白非报错）；重启后端后刷新页面历史仍在；
7. 设置面板清空日志：提示已清除数量，当前运行日志保留；
8. 边界场景：不选文件点分析（友好提示不发请求）、分析中重新选文件（旧进度作废旧结果清空）、分析中关掉后端（提示连接失败，不白屏）。

## 三、接口速查

> 后端接口统一使用双 `/api` 前缀（如 `/api/api/batch/init`），为历史契约保留，详见 `prompt.md` 第 3 节。

| 接口 | 方法 | 作用 |
|---|---|---|
| `/` | GET | 健康检查：服务状态、模型是否加载 |
| `/api/api/batch/init` | POST | 创建批次并上传图片（字段 `files` 可重复，`conf` 阈值） |
| `/api/api/batch/run` | POST | 启动批次后台识别（立即返回） |
| `/api/api/batch/status/{批次ID}` | GET | 轮询批次进度与逐张状态 |
| `/api/api/batches` | GET | 历史批次列表 |
| `/api/api/records` | GET | 检测记录（SQLite 持久化，重启可查） |
| `/api/api/detect` | POST | 单张同步检测（兼容接口） |
| `/api/api/logs/clear` | POST | 清空历史日志文件 |
| `/static/**` | GET | 上传原图与识别结果图的静态访问 |

## 四、启动方式

**环境要求**：Windows + Conda 环境 `yolo_v1`（已包含全部依赖）。

```powershell
# 1. 进入项目根目录（必须在根目录启动，否则找不到模型与静态目录）
cd E:\claude code\Project\2D-Crack-Detection-System

# 2. 启动后端（两种方式任选其一）
conda activate yolo_v1
python backend/main.py
# 或直接指定解释器：
D:\miniconda3\envs\yolo_v1\python.exe backend/main.py

# 3. 启动前端：双击打开 水工建筑物智能巡检分析系统.html（或拖入浏览器）
```

- 后端地址：`http://127.0.0.1:8000`，启动成功后控制台会打印监听信息，`log/` 下生成本次运行日志；
- 前端打开后自动探测后端状态，绿色即代表就绪，即可选择图片开始分析；
- 关闭后端：直接关闭控制台窗口（或任务管理器结束进程），下次启动会自动清理残留锁文件。

## 五、常见问题

1. **提示"已有实例正在运行"**：后端同一时间只允许启动一个实例，属正常保护；若确认没有实例在跑，删除 `backend/running.lock` 后重启即可（进程被强制结束时可能残留）。
2. **端口被占用（WinError 10048）**：执行 `netstat -ano | findstr :8000` 找到占用进程并结束，再启动后端。
3. **前端红色提示"后端未启动"**：先按上述步骤启动后端，再刷新页面。
4. **必须从根目录启动**：模型 `version2.pt`、日志目录、静态目录均按相对路径定位，从其他目录启动会加载失败。
5. **批次文件夹名中的全角冒号**：Windows 文件名不允许半角冒号，故日志与批次目录时间戳使用全角冒号（`：`），属正常现象。

## 六、当前局限与改进方向

立足校级创新训练项目的定位，当前版本优先保证核心识别功能完整可用，以下方面留待后续迭代：

1. **推理速度**：当前固定使用 CPU 推理以保证兼容性，大批量图片处理耗时较长；后续可加入 GPU 加速，显著提升批量识别效率。
2. **缺陷种类**：目前仅支持裂缝（crack）单类别识别，与背景中"逐步扩展识别缺陷种类"的规划一致，后续将随训练数据扩充类别。
3. **识别精度**：精度依赖训练数据的规模与多样性，对光照、纹理等复杂现场条件的泛化能力有待更多实测数据持续优化。
4. **交互实时性**：进度采用每秒轮询方式获取，后续可升级为 WebSocket/SSE 推送，图片多时更节省资源。
5. **存储管理**：识别结果会持续占用磁盘，暂未提供自动清理策略；历史记录查询暂未提供分页，数据量极大时可考虑补充。
6. **使用场景**：系统定位为本地单用户工具，未设计多用户并发与权限管理，后续如需多人协同可在此方向扩展。
